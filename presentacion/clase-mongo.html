¿Por qué aparecen las bases NoSQL?

Alrededor del 2000, con la Web masiva, las bases relacionales empiezan a quedar chicas en cuatro frentes:

Escalabilidad

Volúmenes de datos que no entran en una máquina (BigTable, 2005).

Performance web

Formatos fáciles de serializar y servir: JSON (1999).

Flexibilidad

Que la estructura evolucione sin ALTER TABLE sobre millones de filas.

Distribución

Replicar y fragmentar automáticamente: disponibilidad y tolerancia a fallas.

Hoy usamos MongoDB para ver cómo resuelve cada uno… y qué cuesta.

  • NoSQL Parte I, p. 4-5.
  • Las 4 necesidades son el hilo de la clase: flexibilidad (bloque 1), escalabilidad y distribución (bloque 2), procesamiento (bloque 3).

Mismo mundo, otras palabras

database / schema→database tabla→colección fila→documento (JSON / BSON) columna→campo JOIN→documento embebido (o $lookup)

BSON = JSON binario con más tipos: Date, ObjectId, enteros de 32/64 bits, decimales… Pero sin un esquema que lo controle.

  • Diapo de la cátedra, "Terminología".
  • Remarcar: la equivalencia es aproximada; lo distinto es que el documento puede tener estructura anidada y variable.

¿Dónde va el dueño? Embeber vs. referenciar

    
Un dato relacionado: ¿va adentro del documento o en otra colección?

    

      

        
Embeber: el dueño adentro del auto


// autos
{ _id: "BG 135 ZT", marca: "Toyota",
  dueño: { dni: 21222324, nombre: "Graciela" } }


db.autos.find({ _id: "BG 135 ZT" })

        
+ Un acceso y ya viene el dueño.
− 3 autos = 3 copias de Graciela.

      

      

        
Referenciar: como en SQL


// autos                         // conductores
{ _id: "BG 135 ZT",           { _id: 21222324,
  dueño: 21222324 }               nombre: "Graciela" }


db.autos.aggregate([{ $lookup: {
  from: "conductores", localField: "dueño",
  foreignField: "_id", as: "dueño" } }])

        
+ Graciela existe una vez.
− Leer juntos = $lookup (JOIN, más caro).

      

    

    
En los tweets: user y retweeted_status están embebidos: copias de ese momento.

    
Embebé lo que se lee junto y no crece sin límite. Referenciá lo compartido, lo que cambia seguido o crece sin techo.

  

  
  • Es la pregunta de la diapo de conductores: "¿queremos guardar esto?". Si Graciela cambia el apellido, con embebido hay que actualizar sus 3 autos.
  • En los tweets, el retweet_count dentro de retweeted_status quedó congelado en el momento del retweet.
  • Embeber también da atomicidad gratis: un update a un documento es atómico. Límite: 16 MB por documento.
  • NoSQL Parte I, p. 35-36 (bases orientadas a documentos).
  • Volvemos a esta pregunta en Pizzagram: ¿comentarios embebidos en la publicación?

Replicación: un replica set

    
    

      
Aplicaciónescribe y lee

      
→

      

        
Nodo A · primariorecibe todas las escrituras

        
Nodo B · secundariocopia el oplog del primario

        
Nodo C · secundariocopia el oplog del primario

      

      

        
Las escrituras van al primario; los secundarios las replican de forma asíncrona.

        
Se cae el primario.

        
Los que quedan votan y uno pasa a primario (≈ segundos). Por eso conviene un número impar de miembros con voto (o un árbitro).

      

    

    

      
Write concern w: "majority": confirmar recién cuando la mayoría tiene la escritura.

      
Read preference secondary: leer de un secundario… ¿con datos viejos?

    

  

  
  • NoSQL Parte I, p. 14 (replicación).
  • Atlas te da por defecto un replica set de 3 nodos: el cluster del taller es uno.






  

    
¿Qué ve quien lee de un secundario?

    
    

      
Secuencial / fuerte
Todos ven las escrituras en el mismo orden. Leer del primario con majority.

      
Causal
Si A causó B, nadie ve B sin A. Mongo: causally consistent sessions.

      
Eventual
Si dejan de escribir, en algún momento todos coinciden. Como Dynamo.

    

  

  
  • NoSQL Parte I, p. 22-31.
  • La lectura en rojo es válida bajo consistencia eventual: la réplica todavía no recibió la escritura.






  

    
Sharding: fragmentación horizontal

    
Cuando los datos (o las escrituras) no entran en una máquina: se reparten los documentos entre varios shards.

    

      
Aplicación

      
mongos · routersabe qué rango de la shard key vive en cada shard (config servers)

      

        
Shard 1replica set
Shard 2replica set
Shard 3replica set
Shard 4replica set

      

    

    
La decisión más importante: ¿por qué campo partimos? → la shard key.

  

  
  • NoSQL Parte I, p. 13 (fragmentación horizontal).
  • Cada shard es a su vez un replica set: sharding escala, replicación da disponibilidad. Se combinan.
  • Los números que siguen son reales: simulamos 4 shards sobre los 100k tweets.






  

    
Shard key por rango de created_at

    

      

      

    

    
Hotspot: la fecha siempre crece. A las 23 h, todas las escrituras nuevas van al shard del último rango; los otros tres están ociosos. Y con rangos fijos, lo guardado depende de la hora del día (el de 06 a 12 h tiene menos de un tercio que los otros; Mongo lo compensa partiendo y moviendo chunks, pero las inserciones nuevas siguen yendo todas al último).

    
A favor: "los tweets entre las 21 y las 22" va a un solo shard (consulta por rango dirigida).

  

  
  • Horas en UTC: el pozo de 6 a 9 UTC son las 3 a 6 de la mañana en Argentina.
  • Clave monotónica = escrituras concentradas. Mismo problema con un ObjectId o un autoincremental.






  

    
Shard key hashed por user_id

    

      

      

    

    

      
54.877 usuarios distintos → reparto parejo de datos y de escrituras. "Los tweets de un usuario" sigue yendo a un shard.
Pero: un rango de fechas ahora va a todos.

      
Baja cardinalidad: todo "es" (86%) es un único valor: no se puede partir. Un shard se lleva casi todo.

    

  

  
  • Simulamos con hash mod 4 para ver el reparto. Ojo: con mod N, agregar un shard reubica casi todas las claves. Por eso Dynamo usa hashing consistente (un anillo; NoSQL Parte I, p. 20-21) y Mongo parte el espacio del hash en rangos (chunks) que el balanceador mueve.
  • Una buena shard key: alta cardinalidad, distribución pareja, y que aparezca en las consultas frecuentes.

Teorema CAP

    

      
      

        
Consistencia: todos ven el mismo dato. Availability: siempre hay respuesta. Partition tolerance: sigue andando si se corta la red.

        
En un sistema distribuido las particiones van a pasar: la elección real es entre C y A durante la partición.

        
MongoDB (por defecto): CP. Sin mayoría no hay primario → no acepta escrituras hasta elegir uno.

        
Dynamo, Cassandra: AP. Siempre responden; se reconcilia después (consistencia eventual).

        
Con readPreference: secondary las lecturas siguen respondiendo sin primario (quizás con datos viejos): se corre hacia A. Las escrituras, sin primario, no. BASE vs ACID: es un dial, no un binario.

      

    

  

  
  • NoSQL Parte I, p. 73-78.
  • BASE: Basically Available, Soft state, Eventually consistent.

A la vuelta: el pipeline de agregación, y un ejercicio de parcial.

  







  

    
find filtra. aggregate transforma.

    
Un pipeline es una tubería: cada etapa recibe documentos, hace una cosa y le pasa el resultado a la siguiente. Como cat | grep | sort | head.

    

      
$matchfiltra

      
$groupagrupa

      
$sortordena

      
$limitcorta

    


db.coleccion.aggregate([ { etapa1 }, { etapa2 }, …, { etapaN } ])

    
La salida de una etapa ya no son los documentos originales: después de un $group, solo existe lo que el group generó.

  

  
  • Esta frase es la que más errores evita en Pizzagram: después del primer group, el campo es $_id.ip, no $comentarios.ip.






  

    
Lo que ya saben, con otros nombres

    

      WHERE→$match
      GROUP BY + COUNT/SUM/AVG→$group + $sum / $avg / $max / $push
      HAVING→$match después del $group
      SELECT a, b AS c→$project / $addFields
      ORDER BY · LIMIT · OFFSET→$sort · $limit · $skip
      (no hay)→$unwind
    

  

  
  • Diferencia clave: en SQL el orden lógico lo fija el lenguaje (FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY). En Mongo lo elegís vos, etapa por etapa, y podés repetir etapas.
  • $unwind existe porque en SQL los arrays ya serían filas de otra tabla.

Cerrando: ¿y en SQL? ¿Y el modelo?

    


SELECT ip, COUNT(*) AS cantidad_pizzerias
FROM (
  SELECT p.pizzeria, c.ip
  FROM comentarios c
  JOIN publicaciones p ON p.id = c.id_publicacion
  GROUP BY p.pizzeria, c.ip
  HAVING COUNT(*) = 10
) bots
GROUP BY ip
ORDER BY cantidad_pizzerias DESC
LIMIT 1;

      

        
Misma idea: doble GROUP BY con un HAVING en el medio. El $unwind es el JOIN que no hizo falta.

        
Una publicación viral con miles de comentarios: el documento crece sin límite (16 MB), y cada comentario nuevo reescribe la publicación.

        
Alternativas: comentarios en su propia colección (con pizzeria copiada para no hacer $lookup) o el bucket pattern (de a 100 por documento).

Lo que nos llevamos

    

      
1 · Documentos
Flexibles y cómodos desde el código. El esquema pasa a la aplicación: un typo es un [ ].

      
2 · Escala
Índices para no leer todo. Réplicas para no caerse. Shards para crecer: la shard key decide todo. CAP: es un dial.

    

    

      
3 · Pipeline
Etapas que transforman. Después de un $group solo existe lo que el group generó. El $ importa.

      
4 · Pizzagram
$unwind → $group compuesto → $match → $group → $sort/$limit/$project.
